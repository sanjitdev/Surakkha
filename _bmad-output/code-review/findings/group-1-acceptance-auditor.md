## Findings

- **AC4 — Wrong log method (console.warn instead of console.info)** — AC4 explicitly requires `console.info({ event: 'incident_transition', ... })` and a separate `console.info({ event: 'incident_auto_created', ... })`. The router emits `console.warn(JSON.stringify({ event: "incident_transition", ... }))` and the auto-create path in `applyTransition.ts` also emits `console.warn`. No `incident_auto_created` event key is emitted at all — the auto-create log reuses `event: "incident_transition"` with `verb: "auto_create"`, which violates the "separate log line" requirement. AC4: VIOLATED.

- **AC7 — Log uses `invalid_transition_attempt` (no underscores), not `__invalid_transition_attempt`** — Spec requires the audit shape `event: '__invalid_transition_attempt'`. The actual emit in `applyTransition.ts` and the `IncidentEventType_` Prisma enum use the single-underscore form `invalid_transition_attempt`. The double-underscore name is the v1 stand-in shape for Epic 5.3's `AuditLog` table per the spec; using the DB enum's value as the log event key collapses the wire-AuditLog shape with the in-band enum and is a documented deviation. AC7: VIOLATED.

- **AC8 — Coverage matrix is structural, not semantic** — `transitions.spec.ts` walks every (state × verb) cell but the structural-walk test accepts `undefined` (invalid) as a valid value, so an accidentally-missing INVALID cell would pass. A full per-cell invalid sweep is not present. Cells like `ACKNOWLEDGED + acknowledge`, `ACKNOWLEDGED + resolve`, `ACKNOWLEDGED + reopen`, `INSPECTING + acknowledge`, `INSPECTING + assign`, `INSPECTING + resolve`, `INSPECTING + reopen`, `SAFE + acknowledge`, `SAFE + assign`, `SAFE + submit_result`, `SAFE + reopen`, `UNSAFE + acknowledge`, `UNSAFE + assign`, `UNSAFE + submit_result`, `UNSAFE + reopen`, `MONITORING + acknowledge`, `MONITORING + assign`, `MONITORING + submit_result`, `MONITORING + reopen`, `RESOLVED + assign`, `RESOLVED + resolve` are NOT each pinned with an explicit assertion. AC8: PARTIAL.

- **AC10 — seedUsers.ts exists but no `db:seed` script wiring visible in diff** — The seed file is present and idempotent (`prisma.user.upsert` with `update: {}`), but the spec code map calls for `packages/db/prisma/package.json` MODIFY to add `db:seed`. No modification of `packages/db/prisma/package.json` appears in the diff. The seed is therefore not wired to `pnpm db:seed`. Additionally, the seed file runs `main()` at module load (top-level `main().catch(...)`) rather than exporting for `prisma db seed`'s expected entrypoint, so even adding a `db:seed` script later would require refactoring. AC10: PARTIAL.

- **AC1 / AC2 — Signature drift from canonical TransitionResult shape** — The spec "Implementation notes (locked)" pins TransitionResult with field name `nextIncident` (and `eventType`); the canonical shared type in `packages/shared/src/incident.ts` defines `next_state` / `event_type` / `event_payload`. The implementation in `transitions.ts` correctly returns the canonical shape (`next_state`, `event_type`, `event_payload`, `at`), so this is MET for the runtime — but the spec doc text in §"Implementation notes (locked)" is stale and contradicts the actual code. Flag for the triager: the locked-spec text disagrees with the canonical shared types, and the implementation agrees with the canonical types. This is a SPEC-vs-code deviation in the spec itself, not in the diff.

- **AC5 — Schema is added, but no wire test pins the emit call (verification gap)** — `IncidentOpenedEventSchema` is exported from `packages/shared/src/events.ts` and the emit is wired in `applyTransition.ts`. The `hooks.spec.ts` test asserts the three emits (`alert:opened`, two `incident:opened`s). However, the spec pins "Wire test pins schema; live test pins emit call" — the schema pin is a parse-and-return check in the emit site (`safeParse` on `incidentPayload`), but there is no dedicated schema-spec test asserting `IncidentOpenedEventSchema.parse({...})` directly. AC5: PARTIAL (verification gap).

- **AC6 — Optimistic-concurrency loser path: response omits actual current state** — `applyTransition` throws `OptimisticConcurrencyError` when `updateMany.count === 0`; `commitTransition` catches it, writes an `invalid_transition_attempt` event via `writeInvalidAttemptEvent`, and responds `409 invalid_state_transition` with `reason: "concurrent_modification"`. The spec says the 409 should include "the actual current state" — the response shape here only includes `reason: "concurrent_modification"`, not the current `from`. The IncidentEvent `payload.from` is the pre-update `currentRow.state`, which IS the actor's view of state (not the actual current state after the concurrent writer's update). The audit event captures the actor's view, but the response body does not surface the actual current state to the loser. Partial deviation from spec intent.

- **AC9 — Migration is forward-only** — `20260827000000_incident_state/migration.sql` creates the four enums (`IncidentState_`, `IncidentEventType_`, `UserRole_`, `NotificationSeverity_`, `NotificationRecipientRole_`), the four new tables (`User`, `IncidentEvent`, `Notification`, `Attachment`), adds the four new `Incident` columns with `state DEFAULT 'OPEN'`, adds indexes, and adds all FKs. Forward-only; no destructive changes. AC9: MET.

- **AC3 — Atomicity pinned (structurally)** — `applyTransition` runs `updateMany` → `incidentEvent.create` → optional `notification.create` inside a single `repo.$transaction(async (tx) => {...})` block. Any throw inside rolls back the trio. The atomicity contract is structurally honored; the pinning test is missing from this diff but expected in the live test rig per the spec. AC3: MET for the diff scope.

- **AC2 — REOPENED alias handling** — Spec says "REOPENED alias maps RESOLVED + reopen → OPEN … REOPENED is a transition alias, not a stored state." Implementation: `TRANSITIONS.RESOLVED.reopen = "OPEN"` (correct), `TRANSITIONS.REOPENED = {}` (empty alias, every verb INVALID). The reopen router test confirms the next state is `OPEN`. AC2: MET.
