**Finding 1 (critical)**: VITE_API_BASE_URL in `.env.example` is wired to nothing
  - File: `packages/web/.env.example:11` plus `packages/web/src/main.tsx:122` (`API_ORIGIN = "/api"`)
  - Adversarial input: Operator configures `VITE_API_BASE_URL=http://api:3000` (the documented docker-compose shape) and starts the container. The Vite build inlines `import.meta.env.VITE_API_BASE_URL`, but no code reads it. The apiClient still uses the hard-coded literal `"/api"` from `main.tsx:122`. Conversely, the env.example comment claims `http://localhost:3000` is the docker-compose address, which is wrong (it documents vite-dev). Net result: the only env knob in the file is dead, and the comment is wrong.
  - Impact: Silent misconfiguration. In docker-compose Story 6.1 the web will fail to reach `http://api:3000` because the SPA hard-codes `/api`; in `vite dev` the Vite proxy forwards `/api/*` so the env value is unreachable. An operator who reads `.env.example` and trusts it ends up with a non-functional simulator tab (api calls return 404 / network errors) and there is no diagnostic.
  - Suggested fix: Either (a) actually consume `VITE_API_BASE_URL` in `apiClient.ts` (use `import.meta.env.VITE_API_BASE_URL ?? "/api"` so vite dev still works), and remove the `API_ORIGIN` literal from `main.tsx`; or (b) delete the `.env.example` line entirely and document that the SPA uses the same-origin `/api` proxy. Also fix the wrong docker-compose claim — docker-compose is `http://api:3000`, vite dev is `localhost:3000` *proxied*, not a direct browser origin.

**Finding 2 (critical)**: Token refresh failure during `useSimulatorDevices` query navigates to /login but bypasses the in-flight loading state
  - File: `packages/web/src/admin/simulator/useSimulatorDevices.ts:59-69` plus `packages/web/src/api/apiClient.ts:222-244`
  - Adversarial input: Admin's access token has just expired. TanStack Query kicks off `GET /admin/simulator/devices`. The queryFn receives a 401, apiClient triggers `/auth/refresh`. Refresh fails (revoked session). apiClient calls `config.navigate("/login?next=...")` and returns the original 401 Response. The queryFn then `throw new Error(...)` — *after* navigation has fired. React then re-renders the page with the login screen, but TanStack-Query briefly enters the error state for the simulator query and will retry on the next refetch cycle, which re-runs the same flow in an infinite loop until the user actually navigates away (the `next` keeps being `/admin/simulator` so it lands back here).
  - Impact: A 401-driven navigation to /login doesn't actually settle; once the user logs back in (or the page rehydrates) the simulator page re-mounts and immediately triggers another /devices fetch that 401's again because the tokenStore is briefly empty. Combined with the queryClient's `retry: 1`, the user sees a flicker loop between the login shell and the simulator page on every reload with a stale token.
  - Suggested fix: Either (a) catch the navigate side-effect in `apiFetch` and return a sentinel that signals "redirected, do not retry"; or (b) short-circuit the queryFn when `useTokenStore.getState().accessToken === null` after a navigation has been scheduled; or (c) listen for the navigate in `queryClient.ts` via `queryCache.subscribe` and cancel in-flight queries when the user navigates to /login. At minimum, document that refresh-failure navigate is incompatible with TanStack-Query's retry loop and add a `meta: { skipRetryOnAuth: true }` opt-out.

  - File: `packages/web/src/admin/simulator/useSimulatorDevices.ts:40-57`

  - File: `packages/web/src/admin/simulator/useSimulatorDevices.ts:5-13` plus `packages/web/src/admin/simulator/DeviceRow.tsx:142-156`

**Finding 7 (major)**: `useSwitchScenario` is instantiated per-row with shared keys — invalidation is global, not per-device
  - File: `packages/web/src/admin/simulator/useSimulatorDevices.ts:105-154` plus `packages/web/src/admin/simulator/DeviceRow.tsx:35-40`
  - Adversarial input: Each DeviceRow calls `useSwitchScenario()` independently, creating a separate `useMutation` instance. The `mutationFn` POSTs to a per-device URL, but the `onSuccess` callback calls `qc.invalidateQueries({ queryKey: ["admin", "simulator", "devices"] })`. That's a coarse invalidation that refetches the entire device list. Six rows × simultaneous Switch clicks × coarse refetch = N² refetches / sec. Worse, the rows have their own `useState`s for `selected` and `paused` that DON'T get reset by the refetch (see Finding 6).
  - Impact: Refetch storm. With a few concurrent admins or a flaky network, this hammers `/admin/simulator/devices` six times per switch. Combined with `refetchOnWindowFocus: false` (good), the storm is bounded by user actions — but a single user with six rapid clicks causes one refetch per click. TanStack-Query's `staleTime: 5_000` doesn't help here because `invalidateQueries` ignores staleTime.
  - Suggested fix: Either narrow the invalidation to the affected device (`qc.setQueryData(["admin", "simulator", "device", vars.deviceId], next)` after merging the optimistic result from the mutation's return value); or hoist `useSwitchScenario` to the page level so the same mutation instance handles all rows; or move the switch return into the cache directly: `qc.setQueryData(["admin", "simulator", "devices"], (prev) => ({ ...prev, devices: prev.devices.map(d => d.device_id === vars.deviceId ? { ...d, scenario: vars.scenario ?? d.scenario } : d) }))`.

**Finding 8 (major)**: Mutation type contract throws a class that doesn't extend the declared error type
  - File: `packages/web/src/admin/simulator/useSimulatorDevices.ts:89-97, 105-153`
  - Adversarial input: The `useMutation` is typed `<{ applied: true }, SwitchScenarioError, SwitchScenarioVars>`. TanStack-Query's `useMutation` infers the thrown error type from the second generic. But the implementation throws `new SimulatorSwitchError(detail)` — a class extending `Error`, NOT extending `SwitchScenarioError`. The detail is hung off `.detail`, so consumers who try to read `err.kind` from the thrown value will read `undefined` and crash.
  - Impact: `mutation.error.kind` in DeviceRow's `onError` is `undefined`. The `errorMessage(err)` switch in `SimulatorPage.tsx:42-55` falls through every case to `unknown` (which doesn't match `err.kind === "unknown"` because `err.kind` is undefined), or — more likely — TypeScript complains at the consumer because `err` is typed as `SwitchScenarioError` but the actual thrown value is `Error`. At runtime the switch hits `case "unknown":` only if `err.kind === "unknown"`, otherwise no case matches and the function returns `undefined`. Toast message is `undefined`. The test suite mocks with a synthetic error, so the production bug isn't caught.
  - Suggested fix: Two options. (a) Throw the `detail` object directly: `throw detail as unknown as Error` — but that breaks the typed contract. (b) Make `SimulatorSwitchError` accept a generic `T extends string` so the thrown value's type matches `SwitchScenarioError`. Or (c) change the mutation's error generic to `Error & { detail: SwitchScenarioError }` and have consumers read `err.detail.kind`. Or (d) drop the class wrapper entirely and throw `detail` after a sentinel check.

**Finding 10 (major)**: `pushToast` ID collision possible on the same ms with `Math.random() < 1e-15`
  - File: `packages/web/src/admin/simulator/SimulatorPage.tsx:62-68`
  - Adversarial input: `Date.now() + Math.random()` produces two floats. Math.random() returns a value in [0,1). Adding them yields a unique-per-millisecond value unless two toasts land in the *exact* same millisecond AND `Math.random()` returns the same value (probability ~2^-52). Not likely in practice — but: two rows failing in the same render cycle (e.g., bulk operation triggered by some upstream logic, or rapid user clicks) both fire `pushToast` synchronously, `Date.now()` is identical, and React batches both `setToasts` calls so both `setTimeout` timers schedule the same `id`. The smaller `Math.random()` filters first; the larger one vanishes 4 s later. Or, worse, both happen to compute the same float and one toast silently disappears immediately.
  - Impact: A toast might silently disappear. Not security-critical, but the spec says toasts auto-dismiss; missing-dismiss looks like the toast never existed.
  - Suggested fix: Use a monotonically-increasing ref-based counter: `const idRef = useRef(0); ... id: ++idRef.current`. Cheaper, deterministic, immune to clock skew and randomness collisions.

**Finding 11 (major)**: `setTimeout` in `pushToast` is not cleaned up on unmount — setState after unmount
  - File: `packages/web/src/admin/simulator/SimulatorPage.tsx:62-68`
  - Adversarial input: Admin triggers Switch on device A, navigates away (route change unmounts `SimulatorPage`) before the 4 s timer fires. The timer calls `setToasts((cur) => cur.filter(...))` on an unmounted component. React 18 silently swallows the warning in production but StrictMode in dev doubles the effect. More critically: if the user re-mounts the page 4 s later, the timer fires, calls `setToasts` on a NEW mount, the filter is a no-op (the new toasts state has different ids), but the empty-filter callback still runs a `setState` on the new instance, causing an unnecessary re-render.
  - Impact: Memory leak in long sessions with many toast churns (each unmounted timer holds the setState closure for 4 s). Not a crash, but accumulatively bad.
  - Suggested fix: Track timer handles in a `useRef<Set<number>>` and clear them in a `useEffect(() => () => clearAll, [])` cleanup. Or move the timer into a `useEffect` keyed on `toasts.length` that schedules the dismiss.
