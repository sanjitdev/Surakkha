## Intent

**Problem:** Story 3.2's rules engine reads from the `Rule` table at boot, but the table is empty after `prisma migrate deploy`. Without a default threshold set, every demo run sees a silent engine that never fires — the demo cannot prove end-to-end alert behaviour, and Story 3.7's `/admin/thresholds` tab has nothing to override.

**Approach:** Extend `packages/db/prisma/seed.ts` (which already exists for Story 2.5 device backfill) so a single `pnpm --filter @surakkha/db seed` invocation upserts the nine BRD §8.3.1 global rules alongside the six device rows. The threshold table is the runtime source of truth — at boot, Story 3.2 hydrates from it; admins override per device via Story 3.7. The nine rows are pinned in `packages/db/prisma/thresholdTable.ts` (a pure module) so unit tests can assert exact metric / operator / threshold / severity values without booting Prisma, and so any drift from the BRD fails CI before production.

## Boundaries & Constraints

**Always:**
- The seeded rules are GLOBAL (`deviceId: null`), `version: 1`, `isActive: true`, `ruleType: "instant"` (per the AC list — all nine are instantaneous thresholds), with `createdBy: null` (no User FK yet) and the de-bounce fields zeroed (`minDurationSeconds: 0`, `hysteresisSeconds: 0`). Story 3.4 may revise the zero defaults; this story ships them at zero.
- The exact nine rules are pinned in a pure module (`packages/db/prisma/thresholdTable.ts`) — same nine rows the AC and BRD §8.3.1 list, no more, no less. A test pins the exact `(metric, operator, threshold, severity)` tuple set so a typo'd operator (`gtt` vs `gte`) or a swapped threshold (`0.2` vs `2.0`) fails CI before production.
- The wire symbols (`<`, `>`, `<=`, `>=`, `==`) used in FR-13 / the AC are AC shorthand — the seed writes the matching Prisma enum token (`lt`, `gt`, `lte`, `gte`, `eq`) into the `Rule.operator` column. The wire→Prisma mapping table lives in the seed's helper module, not in the engine (Story 3.2's engine reads the Prisma token directly). The mapping covers exactly the 5 FR-12 operators; v1 ships no `!=` / `<>` semantics.
- Seed is idempotent: re-running `pnpm -F @surakkha/db seed` never duplicates a row. The upsert key is `(deviceId, metric, operator, threshold, version)` — the existing `@@unique` constraint guarantees at-most-one row per combination. Same-shape re-runs are a no-op; a row with a conflicting `version` fails the unique constraint and surfaces as a P2002 — the seed aborts with a clear error rather than silently overwriting.
- The seed runs AFTER `prisma migrate deploy` (which is a separate command — same convention the Story 2.5 device seed follows). The seed does NOT call `prisma migrate deploy` itself.
- The threshold table imports `RuleMetric`, `RuleOperator`, `RuleSeverity` from `@surakkha/shared` (Story 3.1's single source of truth). A drift between the seed's literals and the Prisma enum values fails `tsc`.
- All existing 649 tests keep passing against the regenerated Prisma client.
- The seed's behaviour for the `Device` rows (Story 2.5) is unchanged; the new rule-insert loop runs AFTER the device loop in the same `main()` so the existing test matrix stays green.

**Ask First:**
- Adding per-device default overrides (e.g. a stricter `tds_ppm` for one school). **Default: NO — v1 ships only the global BRD set; per-device override is a Story 3.7 / operator-config story.**
- Wiring the rule insert into a Prisma migration rather than the seed script. **Default: NO — seeds are idempotent runtime data; migrations are forward-only DDL. Conflating the two breaks `prisma migrate deploy` and any CI environment that expects clean migrations.**

**Never:**
- Do not change the existing `Device` upsert loop in `seed.ts` (Story 2.5's contract).
- Do not introduce `Alert`, `AuditLog`, or `User` writes — those land in Stories 3.5, Epic 5, and the User migration respectively.
- Do not call `prisma.rule.create` or `prisma.rule.update` in the seed's rule loop — use `prisma.rule.upsert` keyed on `@@unique([deviceId, metric, operator, threshold, version])` so the seed is the only writer of `Rule` v1 and a second `pnpm -F @surakkha/db seed` run is a no-op.
- Do not seed rules with `deviceId` set — v1 ships only the global BRD set per FR-13 and the AC.
- Do not delete the `seedHelpers.ts` module — it remains the home for pure helpers importable by the spec's test.
- Do not insert rules whose `metric` is not in `RULE_METRICS` or whose `operator` is not in `RULE_OPERATORS` — `tsc` rejects it, but the seed's pure module also asserts at runtime so a future caller that bypasses `tsc` (e.g. a `tsx` script in CI) still surfaces a clear error.

## Design Notes

**Wire-operator symbol → Prisma token mapping is a seed concern, not an engine concern.** FR-13 uses `<` / `>` / `<=` / `>=` / `==` for human readability; the Prisma `RuleOperator` enum (camel-case per Story 3.1's invariant I-5) stores `lt` / `gt` / `lte` / `gte` / `eq`. Story 3.2's engine already maps the stored Prisma token to a JS comparator at evaluation time via its closed lookup table (`OPERATOR_COMPARATORS`). The seed's `WIRE_OPERATOR_TO_PRISMA` is the only place in the codebase where the wire symbol reaches a column value — the engine never sees the wire symbol. This means the wire format can evolve (e.g. adopting a `<>` style negation) without breaking the engine's read path; only the seed helper changes. Adding the mapping table to `thresholdTable.ts` (a pure module) rather than the engine keeps the engine strictly read-only against stored Rule rows.

**Idempotency via `prisma.rule.upsert` on the natural unique key, not a parallel "have I seen this row" set.** The seed wraps every row in `prisma.rule.upsert({ where: <unique-key shape>, create: <full row>, update: {} })`. The empty `update: {}` is the load-bearing detail: Prisma's `@@unique` constraint matches on the `where` key, the `create` branch fires when no row exists at that key, and the `update` branch (empty object) is a no-op when a row exists — the seed never maintains a parallel "have I seen this row" set, the unique constraint is the only authority. The Story 2.5 `Device.upsert` is the same pattern with `update: <partial fields>`; the seed's pattern here has `update: {}` because the rule row's "no overwrite" invariant is stronger than the device row's. Drift detection happens on the returned row's shape vs the desired row — any field mismatch in `{ metric, operator, threshold, severity, ruleType, minDurationSeconds, hysteresisSeconds }` throws the documented error rather than silently overwriting.

**`update: {}` is the only thing standing between "idempotent" and "silent data loss".** A developer who replaces `update: {}` with `update: <row>` (a copy-paste from the Story 2.5 device seed pattern) would pass pure-helper tests but break AC3 (idempotency becomes "silent overwrite"). Block B test (ii) explicitly asserts `prisma.rule.update` is never called. This pin is what makes `update: {}` a load-bearing contract, not an oversight.

**`minDurationSeconds: 0` and `hysteresisSeconds: 0` are the v1 defaults, not a Story 3.4 placeholder.** The two columns are `Int NOT NULL` (per the schema); an instant rule with both at zero fires the instant the comparator matches and clears the instant it no longer matches — the engine treats them as no-op when zero (Story 3.2 pins the absence-rule path's `hysteresisSeconds <= 0 → null` defense-in-depth; for instant rules, both columns are dormant in v1 and Story 3.4 wires them up). Story 3.4 owns the non-zero defaults; this story ships at zero so the BRD defaults work end-to-end today and Story 3.4 layers debounce on top without a backfill. The values appear in the row create payload (and in the drift-checked field set) so a later operator-config story that wants to inspect defaults can read them off the row rather than re-deriving.

**`createdBy: null` because no `User` table exists, and `Rule.createdBy` is intentionally NOT an FK.** The column is forward-compatible per Story 3.1's design notes; today there is no `User` table, so the seed writes the literal `null` rather than fabricating a fake user identifier. When the `User` migration lands in a future story, a follow-up migration adds `references: [id]` on `Rule.createdBy`; the seed's create call gains `createdBy: "seed"` at that point. That change is in the User-migration story, not this one. `createdBy` is NOT drift-checked because the seed does not own the column today — a future migration adding a default admin would flip the value without the seed objecting.

**The seed re-runs safely against a Story-3.7-edited DB — two distinct paths, both handled.** Story 3.7's edit path does one of two things: (a) per-device override — does NOT touch the global `version: 1` row; the seed re-run `upsert`s against the `version: 1` key, finds the row, no-ops. (b) global default edit — increments `version`, inserts a new `version: 2` `isActive: true` row, and flips the original `version: 1` row to `isActive: false`. The seed's `upsertDefaultRule` finds the `version: 1` row at the unique key, sees `isActive: false`, returns `{ status: "skipped-inactive" }`, logs a `preserve-as-is` notice, and continues — the `version: 1` row is preserved (not resurrected, not overwritten). The sibling `version: 2` row is left alone because the seed's unique-key `where` clause scopes to `version: 1`; any future Story 3.7 "reset to defaults" button would have to issue a deliberate `delete` + `create` to undo its own edit, which is the right behavior.

**Shape-drift field set is intentionally narrower than the full row.** The seed checks `{ metric, operator, threshold, severity, ruleType, minDurationSeconds, hysteresisSeconds }` because those are the fields the seed owns. `createdAt` / `updatedAt` are server-generated and not in the seed's control. `version` is part of the unique key (the seed always writes 1, never anything else). `isActive` is the admin-takeover signal (false means "do not resurrect"); it is intentionally NOT drift-checked because `isActive: false` is a valid state. `createdBy` is forward-compat for the User migration; not owned today. A future operation that touches any of these un-checked fields does not trip the seed's drift error.

**Why a separate `thresholdTable.ts` module and not `THRESHOLD_TABLE` in `seed.ts`.** The seed script imports PrismaClient at module scope and is not importable in vitest because of the `process.exit(1)` failure path (`packages/db/prisma/seed.spec.ts` documents this exact constraint — its block-comment note "The full Prisma upsert flow is exercised in the docker-compose stack's boot sequence" describes the trade-off). Putting the constant + mapping + runtime guard in a separate module means the spec test pins the data + the mapping bijection + the guard without booting Prisma. The same approach Story 2.5 takes with `seedHelpers.ts` (and a new `upsertDefaultRule` is the importable seam for the DB-touching part). Block B uses `vi.spyOn(prisma, "rule", ...)` against the importable helper to drive the AC2/AC3/AC5 assertions, sidestepping the `process.exit` constraint entirely.

**`RuleSeedRow` is a deliberately thin DTO.** It carries `{ metric, operator, threshold, severity }` — the four fields a Story 3.7 reset-to-defaults button could conceivably edit through the admin tab. It does NOT carry `ruleType / minDurationSeconds / hysteresisSeconds / version / isActive / createdBy` because those are the seed's permanent invariants — exposing them through the DTO would let a Story 3.7 caller mutate a `ruleType` from `"instant"` to `"rate"` and break the engine's closed-enum contract. The seed fills those invariants internally from a single source of truth (this module).
