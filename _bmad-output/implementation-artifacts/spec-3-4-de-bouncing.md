## Intent

**Problem:** Story 3.2's engine returns raw `BreachResult[]` per frame — every brief blip on `tds_ppm >= 300` produces a breach. With six devices at ~1 reading/sec that's ~500 breaches/day, most of them one-frame noise that spams operators with phantom alerts. FR-14/AR-7 require a two-stage filter: a reading must be in violation for `min_duration_seconds` before an alert opens, and once cleared the reading must stay below threshold for `hysteresis_seconds` before the alert re-fires. Today's engine treats `hysteresisSeconds` only as the absence-window (3.2's dual-semantics pin); the rising-edge / falling-edge timer does not exist.

**Approach:** Add a `RuleDebounceState` table tracking `(deviceId, metric, severity) → { inViolationSince, clearedSince }`, layer a pure `debounceBreaches(rawBreaches, state, rules) → BreachTransition[]` between `evaluateRules` and the alert-writing path, and on the rising-edge write an `Alert` row + emit `alert:opened`. On the falling-edge set `Alert.cleared_at`. The de-bounce key is `(deviceId, metric, severity)` — never `ruleId` — so range rules (`ph<6.5 critical` + `ph>8.5 critical`) share one timer and produce one alert.

## Boundaries & Constraints

**Always:**

- De-bounce key is exactly `(deviceId, metric, severity)` per FR-14. Range-rule halves collapse to one timer; sustained violation of either half counts.
- `minDurationSeconds` and `hysteresisSeconds` are validated as `Number.isFinite(value) && value >= 0` — any negative, NaN, or Infinity is treated as "no rule" (no transition emitted), mirroring 3.2's absence-rule defense-in-depth.
- `RuleDebounceState` lives in Postgres per ADR-3 §"Negative". Every eval reads + writes through Prisma inside a single `$transaction` so the (Alert row, RuleDebounceState row) pair commits atomically.
- `RuleDebounceState.deviceId` is an FK to `Device.id` with `onDelete: Cascade` so a deleted device drops its state rows (no ghost transitions on re-add).
- The de-bounce module is pure — `debounceBreaches(args) → { transitions, nextState }` — so `debounce.spec.ts` runs without any Prisma mock (same seam 3.2 established for the engine).
- The `Alert` schema lands in this story: `id, deviceId, ruleId, severity, metric, openedAt, clearedAt, acknowledgedAt`. `clearedAt` and `acknowledgedAt` default to `null`.
- `Alert` is uniquely keyed per `(deviceId, metric, severity)` such that at most ONE open Alert exists. Implemented as a partial unique index on `(deviceId, metric, severity)` filtered `WHERE clearedAt IS NULL` (Postgres partial index). Provides idempotency without locking the whole table.
- `Alert(deviceId, metric, severity, clearedAt IS NULL)` lookup query: a helper `findOpenAlert(deviceId, metric, severity)` exported from the debounce layer, used by both 3.4 (open and idempotency) and 3.5 (linked-alerts collapse — out of scope here but the lookup is the seam).
- `RuleDebounceState` carries the `@@unique([deviceId, metric, severity])` constraint enforced by the schema — duplicates are impossible at the DB layer.
- `alert:opened` is emitted on the room `device:<deviceId>` (per 3.5's AC). `alert:cleared` is NOT emitted (per 3.5's AC: "UI derives clear from a fresh reading").
- Re-fire after a clear creates a NEW `Alert` row (3.5's `linked_alerts` mechanic may collapse these later — out of scope here).
- Clock skew on `frame.ts`: trusted as-is, but if `frameTs < maxSeenFrameTs` for the same device, log `console.warn` and clamp `inViolationSince` forward to `frameTs` (don't let arithmetic go negative). Auto-recovers on the next in-order frame.
- Rule-version transitions (Story 3.7 hot path): debounce timer continues across rule versions without reset. If old rule `v1` had `min=30` and new `v2` has `min=0`, the timer keeps its current `inViolationSince` and emits `open` immediately on the next breach if it was already past the 30s threshold.
- `EngineRule` grows `minDurationSeconds: number`; `cache.ts`'s `projectRow` adds the field; the engine surface (`evaluateRules`) is unchanged. De-bounce is a layer ABOVE the engine.
- **No audit-log writes in this story.** Epic 5 owns the `AuditLog` table; 3.4 emits `console.warn('[alerts] opened device=<id> rule=<id> severity=<s> openedAt=<iso>')` on open and `'[alerts] cleared alert=<id> clearedAt=<iso>'` on clear. Epic 5 retro-fits the audit rows.

**Ask First:**

- Adding a `maxDurationSeconds` cap that auto-resolves a stuck alert. **Default: NO.**
- Persisting per-rule breach counters. **Default: NO.**
- Deploying with both `minDurationSeconds: 0` AND `hysteresisSeconds: 0` on the same rule (write-amplification risk: a faulty sensor oscillating at 1 Hz produces ~1 open + ~1 clear per second = ~120 Alert rows/min). **Default: NO — operators must set at least one of the two to ≥1.**

**Never:**

- Do not put `inViolationSince` / `clearedSince` in the `Rule` or `Alert` table — they belong on `RuleDebounceState`.
- Do not collapse two severities into one timer. `(device, metric, warning)` and `(device, metric, critical)` run independently.
- Do not touch 3.5's acknowledge flow. 3.4 only writes `openedAt` + `clearedAt`; `acknowledgedAt` stays `null` until 3.5.
- Do not emit `alert:cleared` (3.5's UX contract).
- Do not bypass `evaluateRules` — de-bounce must be a separate unit-testable layer.
- Do not write to a non-existent `AuditLog` table — Epic 5 owns that. Console-log instead.
- Do not let `frameTs - inViolationSince` go negative on clock skew — clamp to 0 and warn.

## I/O & Edge-Case Matrix

| Scenario                  | Input / State                                                                                                                              | Expected Output / Behavior                                                                                                                                   |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| RISING_EDGE               | 30s of `tds_ppm=312` with `min=30` rule                                                                                                    | Frames 1..29: no transition; Frame 30: `{ kind: "open" }`; `Alert` row created; `alert:opened` emitted; `RuleDebounceState` row created/updated              |
| FALLING_EDGE              | After open, frame drops below with `hysteresis=60`                                                                                         | Frames 1..59: no transition; Frame 60: `{ kind: "clear" }`; `Alert.cleared_at` set; no socket event                                                          |
| RANGE_RULE_SHARED_TIMER   | `ph<6.5 critical` + `ph>8.5 critical` with `min=30`; reading oscillates                                                                    | ONE timer; ONE `Alert` row at rising edge (sustained oscillation does NOT reset `inViolationSince`)                                                          |
| FIRST_FRAME_BREACH        | `min=0` rule, frame breaches                                                                                                               | Immediate `{ kind: "open" }`                                                                                                                                 |
| REOPEN_AFTER_CLEAR        | Cleared alert, frame breaches again                                                                                                        | NEW `Alert` row (the closed one stays closed); partial unique index enforces at-most-one-open                                                                |
| TWO_SEVERITIES_SAME_FRAME | Both `tds_ppm>=300 warning` and `tds_ppm>=1000 critical` breach                                                                            | TWO `Alert` rows; TWO independent `RuleDebounceState` rows                                                                                                   |
| POISON_VALUES             | `minDurationSeconds: -1` or `NaN` or `Infinity`                                                                                            | Treated as "no rule"; no transition emitted; `console.warn('[debounce] skipped poison ruleId=<id> minDurationSeconds=<v>')`                                  |
| CLOCK_SKEW                | `frameTs < lastSeenTs` for the same device                                                                                                 | `inViolationSince` clamped forward to `frameTs` (timer restarts); `console.warn('[debounce] clock skew device=<id> frameTs=<iso> lastSeen=<iso>')`           |
| DEVICE_DELETED_CASCADE    | `Device.id` row deleted                                                                                                                    | CASCADE removes all `RuleDebounceState` rows for that device (no ghost timers)                                                                               |
| CONCURRENT_FRAMES         | Two frames within the same ms for the same `(device, metric, severity)`                                                                    | Pure module is concurrency-safe; IO layer wraps in `$transaction` to prevent duplicate Alert rows                                                            |
| STALE_STATE_NO_RULE       | `RuleDebounceState` row exists for `(device, metric, severity)` but no Rule row currently targets that tuple (rule was deactivated in 3.7) | State row stays untouched; next eval that sees zero rules for the slot does NOT clean it up automatically. Out of scope: a future story adds a janitor task. |

New migration file `prisma/migrations/<YYYYMMDDHHMMSS>_alert_debounce/migration.sql` (single file, not a directory).
- `packages/shared/src/events.ts` -- EXTEND: the existing `AlertOpenedEventSchema` (snake_case, at `events.ts:33-40`) is the canonical wire contract. 3.4 keeps its shape but ADDS three fields: `rule_id: z.string().uuid()` (the rule that fired), `value: z.number()` (the reading that breached), and the inferred type alias `AlertOpenedEvent` is re-exported. The spec does NOT introduce a parallel `alertOpenedEventSchema` — the wire contract is the existing one, extended.
- `packages/api/src/rules/debounce.ts` -- NEW. Pure module only. `debounceBreaches({ rawBreaches, currentState, rules, frameTs, deviceId, lastSeenFrameTs }) → { transitions, nextState }`. The pure module does NOT touch Prisma. For each `(metric, severity)` slot: validate BOTH `rule.minDurationSeconds` AND `rule.hysteresisSeconds` with `Number.isFinite(v) && v >= 0`; skip the slot if either is poison. If raw breach present, advance rising-edge: set `inViolationSince = frameTs` on first breach; emit `open` when `frameTs - inViolationSince >= rule.minDurationSeconds * 1000`. If no raw breach, advance falling-edge: set `clearedSince = frameTs` on first clear; emit `clear` when `frameTs - clearedSince >= rule.hysteresisSeconds * 1000`. On `open`, also null out `clearedSince` (the slot is rising, not falling). Apply clock-skew clamp on both `inViolationSince` and `clearedSince`. Pure returns transitions; no IO.
- `packages/api/src/rules/hooks.ts` -- EXTEND `installRuleEngineHooks`: load `RuleDebounceState` for `(deviceId, metrics+severities touched by rules OR rawBreaches)`; call `debounceBreaches`; for each `open`: in a `$transaction` (a) check `findOpenAlert(...)` for idempotency, (b) if none, `prisma.alert.create(...)`, (c) `prisma.ruleDebounceState.upsert(...)`. The `$transaction` runs at the Prisma default isolation (READ COMMITTED); the partial unique index is the safety net for the open race. The hook catches `P2002` from `prisma.alert.create` and treats it as "already-open, skip" (logs `'[alerts] duplicate open suppressed device=<id> ...'`). Emit `alert:opened` AFTER the transaction commits. `console.info('[alerts] opened device=<id> ...')` (info, not warn — normal lifecycle). For each `clear`: in a `$transaction` (a) `prisma.alert.update({ where: { id }, data: { clearedAt } })`, (b) `prisma.ruleDebounceState.upsert(...)` to write `clearedSince`. `console.info('[alerts] cleared alert=<id> ...')`. Track `lastSeenFrameTs` per-device in an in-memory `Map` for clock-skew detection (cleared on api restart; defensive only — see Design Note "lastSeenFrameTs restart semantics").
- `packages/api/src/rules/findOpenAlert.ts` -- NEW. Thin IO helper that wraps the partial-index lookup: `findOpenAlert({ prisma, deviceId, metric, severity }) → Promise<AlertRow | null>`. Lives in its own file (not `debounce.ts`) so the pure module stays Prisma-free; consumed by `hooks.ts` and exposed for Story 3.5.

## Design Notes

**Why a separate `debounce.ts` module and not inlining into the hook.** Same argument 3.2 used for the engine: pure functions are unit-testable without Prisma mocks, and the hook is integration-only. `debounceBreaches(args) → { transitions, nextState }` is the pure core; the hook wraps it with IO. IO is small enough that `hooks.spec.ts` integration tests cover the full path.

**`findOpenAlert` lives in its own file, not in `debounce.ts`.** The pure module is testable without mocking Prisma — that purity is the seam's value. Putting `findOpenAlert` (a `prisma.alert.findFirst` call) inside `debounce.ts` would force every `debounce.spec.ts` test to either mock Prisma or split the file. So `findOpenAlert` is its own file `packages/api/src/rules/findOpenAlert.ts`; `debounce.ts` is pure; the hook composes both.

**Hook return type stays `Promise<readonly BreachResult[]>`.** The shared `IngestHooks` interface (`packages/api/src/ingest/hooks.ts:71`) returns `BreachResult[]`; changing it to `BreachTransition[]` would break the no-op default and any 3.5 consumer that imports `IngestHooks`. So the hook's return type stays as-is, and `BreachTransition` is the type of the IO side-effect emitted by the hook (Alert row + socket event), not the hook's return value. `BreachTransition` is declared in `debounce.ts` as a discriminated union: `{ kind: "open"; alertId; ruleId; metric; severity; deviceId; openedAt } | { kind: "clear"; alertId; clearedAt }`.

**De-bounce key `(deviceId, metric, severity)` is non-negotiable.** FR-14 verbatim: "tracked per (device, metric, severity)". A `ruleId`-keyed implementation would let range-rule halves run independent timers, producing two alerts for one sustained violation — wrong. AR-7 reinforces: "Range rules are expressed as two single-sided rules because v1's instant operators don't support between". The schema enforces the key via `@@unique([deviceId, metric, severity])`.

**`Alert` row creation belongs in 3.4, not 3.5.** 3.5's "alert lifecycle" is acknowledge + log endpoint + audit — not row creation. The rising-edge de-bounce IS the gate that decides when an Alert exists; that gate lives in 3.4. 3.5 picks up the row after creation. `acknowledgedAt` exists in 3.4's schema (default `null`) so 3.5 doesn't need a migration.

**`Alert` row creation is enforced at the DB layer, not at the application layer.** A partial unique index `WHERE clearedAt IS NULL` (in the migration SQL — Prisma `@@unique` does not support WHERE) ensures at-most-one-open Alert per `(device, metric, severity)` even if the application logic races. Application-layer `findOpenAlert` is the fast path; the index is the safety net. If both attempts to create race, the second hits a `P2002` and the hook catches it as "already-open, skip" (logged via `console.info('[alerts] duplicate open suppressed device=<id> ...')`).

**`clearedSince` and `inViolationSince` are both nullable, with rising winning.** Freshly-onboarded device: no `RuleDebounceState` rows; first breach creates the row with `inViolationSince: frame.ts, clearedSince: null`. Long-quiet device: `inViolationSince: null, clearedSince: lastSeen.ts`. Pure module treats `null` as "not currently timing for that edge." On the rising edge (raw breach), `inViolationSince` advances AND `clearedSince` is reset to `null` (rising wins; hysteresis reference is dropped until the next fall). On the falling edge (no raw breach), `clearedSince` advances AND `inViolationSince` is preserved (so the rising timer pauses rather than resets, per AC1).

**Clock-skew clamp applies to BOTH fields, symmetrically.** If `frameTs < lastSeenFrameTs` for the same device, both `inViolationSince` and `clearedSince` clamp forward to `frameTs` and a `console.warn('[debounce] clock skew device=<id> ...')` fires. Rule-version transitions are NOT affected by the clamp (rule-version swap is a separate code path that does not invoke the clamp).

**Socket emit happens post-commit.** If the transaction rolls back after the socket emit (network partition, Redis-pub/sub miss), the client would see an `alert:opened` that doesn't exist in the DB. Emitting AFTER the `$transaction` resolves reverses the risk: if emit fails, the alert exists in the DB and the next eval pass can re-emit (idempotent on `alertId`). The hook uses a `BroadcastTarget` seam (consumed by the existing socket layer) — the seam exposes `emit(event, payload)` so the test suite can capture emits without booting a real socket.

**No audit-log writes in 3.4.** Epic 5's `AuditLog` table lands in a later story; writing to a non-existent table would crash the hook. Lifecycle events use `console.info` (NOT `console.warn` — these are normal events, not anomalies; warn-level logging would generate false-positive alerts in Datadog/Splunk). The Alert row carries `openedAt` and `clearedAt` so the audit pass can derive audit entries from the Alert lifecycle even after the fact. The Epic 5 retro-fit reads Alert rows + `RuleDebounceState` to backfill `AuditLog`.

**Hysteresis is a noise-suppression feature, but masks sensor oscillation.** With `hysteresisSeconds: 0`, an oscillating sensor produces one Alert open + one Alert clear per oscillation cycle (~120 rows/min at 1 Hz); with `hysteresisSeconds: 60`, the operator sees one Alert that never clears during the fault. Both behaviours are defensible: the first gives the operator visibility into oscillation, the second suppresses noise at the cost of clarity. 3.4's job is to honour whichever the Rule row says; the trade-off is documented in the spec and the operator decides per-rule. A future "sensor-fault" event (Epic 5 or later) could detect the oscillation pattern by Alert-row count over a window and surface it without sacrificing hysteresis.

**Alert-write rate limiting is the wire layer's responsibility, not 3.4's.** Story 2.2's rate check at the WS endpoint bounds inbound frames per device; 3.4 inherits that bound. A compromised device that fires thousands of breaching frames can still produce thousands of Alert rows on its own `(device, metric, severity)` keys — that risk is the wire layer's, not 3.4's. 3.4 does not add per-device Alert-write rate limiting.

**Postgres state is the v1 choice per ADR-3; in-memory is a v2 refactor candidate.** ADR-3 §"Negative" is explicit: "alert de-bouncing windows … live in Postgres … Acceptable at v1 scale; a Redis-backed hot path is a clear v2 refactor." 3.4 ships with Postgres state because (a) restart-safety matters — a restart mid-violation must NOT reset the timer — and (b) the multi-process path (if v2 splits the api) needs shared state. The Postgres round-trip per frame is bounded by the wire-layer rate and is acceptable at v1 scale. A v2 in-memory cache (with WAL replay) is the explicit v2 path.

**`lastSeenFrameTs` is process-local by design; restart-safety argument does not require it.** The Map lives in api process memory and resets on restart. The "restart mid-violation must NOT reset the timer" claim is about `RuleDebounceState.inViolationSince` (Postgres, authoritative), not about `lastSeenFrameTs` (Map, defensive only). On restart, the Map is empty; the first post-restart frame's `frameTs < lastSeenFrameTs` check returns `false` (because `lastSeenFrameTs` is `undefined`); clock skew on the first frame is silently ignored. This is acceptable because `inViolationSince` in Postgres survives the restart and the next frame's timestamp comparison is against the persisted value, not the Map.

**Alert cascade chain on Device delete.** `RuleDebounceState.deviceId` → `Device.id` ON DELETE CASCADE; `Alert.deviceId` → `Device.id` ON DELETE CASCADE; `Alert.ruleId` → `Rule.id` ON DELETE CASCADE. A `DELETE FROM "Device"` therefore removes: (1) Device row, (2) cascade Alert rows (via `Alert.deviceId`), (3) cascade `RuleDebounceState` rows (via `RuleDebounceState.deviceId`). Rules referenced by Alert rows do NOT cascade-delete (a Rule is independent of the Device that fires against it); if Rule itself is deleted, the cascade on `Alert.ruleId` removes the Alert rows that reference it.

**Write-amplification boot guard is code-enforced, not documented-only.** `installRuleEngineHooks` runs at boot via `initializeRuleEngine()` (`packages/api/src/index.ts:455`). Before installing the hook, it scans the active Rule cache for any rule with BOTH `minDurationSeconds === 0` AND `hysteresisSeconds === 0`. The guard runs BEFORE the existing `try/catch` (so the existing NOOP_HOOKS fallback does NOT swallow the boot-guard rejection). If any such rule exists, `installRuleEngineHooks` throws `WriteAmplificationError` (extends `Error`, has a stable `name`). `initializeRuleEngine`'s catch recognizes this error type and re-throws to the `boot().catch()` at `index.ts:550` which calls `process.exit(78)` (`EX_CONFIG` from `sysexits.h` — the conventional exit code for "configuration error"). For any other error, the existing NOOP_HOOKS fallback applies (transient DB outages still degrade gracefully; configuration errors do not). The boot guard emits `console.warn('[debounce] write-amplification guard: ruleId=<id> has min=0 AND hysteresis=0')` before throwing. Operators who legitimately want both fields at zero must remove the rule, set one to ≥1, or edit the boot guard with a documented opt-in. The boot guard is pinned by two tests in `hooks.spec.ts`: (a) fake cache with one `min=0, hysteresis=0` rule asserts `WriteAmplificationError` is thrown, (b) fake cache with all rules at `min ≥ 1 OR hysteresis ≥ 1` asserts the hook installs normally.
