## Intent

**Problem:** Story 3.4 (shipped as `feed712`) creates an `Alert` row at the rising edge and emits `alert:opened` on the device room. The row carries `severity, openedAt, clearedAt?, acknowledgedAt?` but those columns are write-only today — there is no operator-facing way to acknowledge an alert (FR-15), no `GET /api/alerts` for the dashboard to render the lifecycle, and no `alert:acknowledged` socket event for live updates. The row is a write-only artefact until 3.5 ships.

**Approach:** Land an idempotent `POST /api/alerts/:alert_id/acknowledge` endpoint (Admin/Operator only per RBAC), a `GET /api/alerts` list endpoint (all 4 roles can read), and the `alert:acknowledged` socket emit on the room `device:<deviceId>`. The list response surfaces `linked_alerts` per row as the **predecessor history** — the most-recent CLOSED alerts sharing the `(device, metric, severity)` key — via a single batched `prisma.alert.findMany({ where: { OR: [...predKeys] } })` lookup (the partial unique index `Alert_open_unique_idx WHERE clearedAt IS NULL` makes a "previous OPEN alert for the same key" structurally impossible, so predecessor = closed alerts). The dashboard renders "this alert is part of an ongoing chain" without waiting for Story 3.6 to land. The `Alert` schema gains `acknowledgedByUserId String?` so the actor is recorded; the column is plain (no FK) because the `User` table lands in Epic 5. Audit-log writes are deferred to Epic 5; 3.5 emits `console.warn` only.

## Boundaries & Constraints

**Always:**

- Acknowledge is idempotent: a second `POST /api/alerts/:alert_id/acknowledge` returns 200 with the ORIGINAL `acknowledgedAt`; the row is NOT re-updated, the `acknowledgedByUserId` is NOT overwritten, and the `alert:acknowledged` event is NOT re-emitted. The dashboard's "Acknowledge" button must never 4xx for an already-acknowledged alert.
- `alert:acknowledged` is emitted ONLY on the first acknowledge (when `acknowledgedAt` transitions from `null` to a timestamp). The event semantically announces a state TRANSITION (unack'd → ack'd), not a request. A re-acknowledge is a no-op as far as the wire is concerned. Pinned by `FIRST_ACK_EMITS_ONLY` test.
- `alert:acknowledged` is emitted AFTER the Prisma update commits (post-commit ordering per 3.4's design note "Socket emit happens post-commit"). If the transaction rolls back, the client does not see the event; the next eval pass / retry re-emits (idempotent on `alert_id`).
- `alert:acknowledged` is emitted on the room `device:<deviceId>` (mirror of 3.4's `alert:opened` room literal).
- `GET /api/alerts` defaults to OPEN-only (`clearedAt IS NULL`). The `?cleared=true|false` filter overrides the default. The dashboard's main view shows active issues; the closed-archive requires an explicit flag.
- `GET /api/alerts` filters compose as AND: `?deviceId=<uuid>`, `?severity=critical|warning|info`, `?acknowledged=true|false`, `?cleared=true|false`. The `?cleared` filter supersedes the default `clearedAt: null` predicate.
- `GET /api/alerts` paginates by `(openedAt DESC, id DESC)` with an opaque cursor base64url-encoded as `{ t: <openedAt.getTime() in ms>, i: <id uuid> }` (number ms, not ISO string — keeps the wire format compact and lossless against Postgres's `DateTime` resolution). The `id` tie-break handles same-millisecond inserts from multiple devices. Default `limit=10`, max `limit=50`.
- `AlertSummary.linked_alerts` is the **predecessor history** for the same `(device, metric, severity)` key — populated by a SINGLE batched `prisma.alert.findMany({ where: { OR: <pageRows.map(r => ({ deviceId: r.deviceId, metric: r.metric, severity: r.severity, id: { not: r.id }, clearedAt: { not: null } }))> }, orderBy: { openedAt: 'desc' }, take: <limit * 5> })` lookup keyed on the page's `(deviceId, metric, severity)` tuples. Per-row mapping: for each page row, find its predecessors by key, slice to 5. The `clearedAt: { not: null }` predicate is load-bearing — the partial unique index `Alert_open_unique_idx WHERE clearedAt IS NULL` (3.4's contract, `packages/db/prisma/schema.prisma:81`) makes "previous OPEN alert" structurally impossible, so the predecessor is always CLOSED. CLOSED rows in the page return `[]` (no further lookup — a closed alert's predecessor lookup would itself be a closed alert, which is the same key — bounded recursion would have to be modelled). Bounded at `limit * 5` rows so the follow-up query does not become an unbounded join; the per-row slice of 5 caps the wire payload at `5 * MAX_LIMIT = 250` linked entries per page.
- The acknowledge endpoint does NOT verify the alert is currently OPEN. A closed-then-reopened alert can be acknowledged in either state — `acknowledgedAt` is set on the latest row (the partial unique index `Alert_open_unique_idx WHERE clearedAt IS NULL` ensures there's at most one OPEN row per key, and `acknowledgedAt` is per-row so a closed-then-new-open pair each carries its own ack timestamp).
- RBAC: `Alert.read` granted to all 4 roles (Admin, Operator, Technician, Viewer); `Alert.acknowledge` granted to Admin + Operator only (NOT Technician, NOT Viewer). The matrix cells are unchanged from `architecture-appendix-rbac.md` lines 47-50 (read) and 100-103 (acknowledge); the 3.5 implementation enforces them via the existing `authorize({ action, resource }, audit)` middleware.
- `Alert.acknowledgedByUserId` is `String?` (nullable; no FK constraint). Epic 5 owns the `User` table; the FK constraint is added in Epic 5's migration. Existing 3.4-shipped rows are valid without backfill (the column is nullable).
- After acknowledge, BOTH `acknowledgedAt` and `acknowledgedByUserId` are set via `prisma.alert.updateMany({ where: { id, acknowledgedAt: null }, data: { acknowledgedAt: <now>, acknowledgedByUserId: <actorUserId> } })` — a single round-trip **compare-and-set** that is atomic at the row level. If `result.count === 1`, the first-ack won the race; emit `alert:acknowledged` post-commit. If `result.count === 0`, a concurrent ack beat us (or the alert was already ack'd at rest) — follow up with `prisma.alert.findUnique({ where: { id } })` and return 200 with the existing `acknowledgedAt` + `acknowledgedByUserId`; NO emit, NO update. The compare-and-set is the safety net for the simultaneous-ack race; the idempotency fast path covers the re-ack-after-commit case. Pinned by `ACK_RACE_LOSER` (new) test: two `updateMany` calls fired concurrently, exactly ONE returns `count === 1`, the other returns 200 with the first's timestamp.
- `AlertAcknowledgedEventSchema` (already in `packages/shared/src/events.ts:49-54`) is the canonical wire contract for `alert:acknowledged`. The payload shape is `{ alert_id: uuid, acknowledged_at: iso8601, actor_user_id: uuid }` (snake_case, all required). The api constructs the payload from `req.now()` (the same `now()` used in the DB write — see AC1c), `req.user.id` (the JWT-claim actor — see AC1b), and the URL path's `alert_id`. 3.5 reuses the existing schema; no new `alertAcknowledgedEventSchema` export. Before emit, the handler runs `AlertAcknowledgedEventSchema.safeParse(payload)`; on parse failure, the emit is skipped (mirror of 3.4's wire-drift handling in `applyTransition.ts:188-199`) and `console.warn('[alerts] ack emit schema drift alertId=<id>')` is logged.
- `actorUserId` is sourced from the authenticated JWT's `userId` claim (i.e. `req.user.id` after the `authorize` middleware has run — the JWT claim attaches as the `.id` property in `req.user` per `AuthorizedRequest.user.id` at `packages/api/src/middleware/authorize.ts:71-86`) — NOT from a request header, NOT from a query param. JWT-claim is the canonical source so the actor is non-spoofable. Pinned by the test rig: the `Operator` token's `userId` claim matches the row's `acknowledgedByUserId` after a successful ack.
- `now` for the acknowledge timestamp is sourced from `req.now()` (an optional injectable clock; default `() => new Date()`) — NOT the database `@default(now())`, NOT a server-side global `Date.now()`. The injectable clock lets tests assert exact values without time-mocking libraries; production wires `now: () => new Date()` once in `packages/api/src/index.ts`. The compare-and-set's `acknowledgedAt` value MUST be the SAME `now()` instance the response body returns (no two reads of the clock — that would risk a 1ms drift between DB row and wire payload).
- Post-commit emit failure path: if `broadcast.to(...).emit(...)` throws, the handler catches the throw, logs `console.warn('[alerts] acknowledge emit failed alertId=<id>')`, and STILL returns 200. The row is committed, the request is semantically successful, and the next eval pass / retry re-emits (idempotent on `alert_id`). The alternative (uncaught throw → 500) would force the client to retry a write that already succeeded, potentially triggering a second `updateMany` round-trip on the next attempt. Pinned by `ACK_EMIT_THROWS` (new) test: stub `BroadcastTarget` throws on emit, response is 200 with the original timestamp + actor.
- `BroadcastTarget` interface is the existing `BroadcastTarget` from `packages/api/src/ingest/frame.ts:84` — `to(room: string): { emit(event: string, payload: unknown): unknown }`. The 3.5 handler calls `broadcast.to(\`device:\${deviceId}\`).emit("alert:acknowledged", payload)`— same shape as 3.4's`alert:opened`emit in`applyTransition.ts:189`. Pinned by `POST_COMMIT_EMIT_ORDERING`+`ACK_EMIT_THROWS`.
- `console.warn('[alerts] acknowledged alertId=<id> actor=<id> acknowledgedAt=<iso>')` on EVERY successful acknowledge (including idempotent re-ack) — operators see who ack'd what and when in the boot log pipeline, even when the wire emit is suppressed. The first-ack line reads `first=true`; the idempotent re-ack line reads `first=false` so log readers can distinguish state-change acks from idempotent retries. Pinned by `CONSOLE_WARN_DISTINCTION` (new) test: stub the logger, fire first ack + re-ack, assert two log lines, the first has `first=true`, the second has `first=false`.

**Ask First:**

- Adding a `maxAckAgeSeconds` window after which the alert can no longer be acknowledged (e.g., a 7-day ack window). **Default: NO** — acknowledge is always allowed regardless of age.
- Persisting an `ack_reason` free-text field. **Default: NO** — the dashboard's "Acknowledge" button is a one-click action with no comment surface. Story 4.5's incident-side `submit_result` carries the analogous "reason" payload (SAFE / UNSAFE / MONITORING); alert acknowledge does not.
- A `POST /api/alerts/:alert_id/unacknowledge` (revert ack). **Default: NO** — the dashboard has no UI surface for this and Story 4.5's reopen path is for the Incident, not the Alert.

**Never:**

- Do not change the partial unique index `Alert_open_unique_idx WHERE clearedAt IS NULL` (3.4's contract).
- Do not change the `IngestHooks.onRuleEvaluation` return type or the `BreachTransition` shape (3.4's contract).
- Do not collapse two severities into one lifecycle row. `(device, metric, warning)` and `(device, metric, critical)` are independent Alert rows with independent `acknowledgedAt` timestamps.
- Do not write to a non-existent `AuditLog` table — Epic 5 owns that. Console-log instead.
- Do not add a `state` field to `Alert` (no state machine; Alert lifecycle is three timestamps: `openedAt, acknowledgedAt?, clearedAt?`).
- Do not emit `alert:cleared` (3.4's UX contract: UI derives clear from a fresh reading).
- Do not re-emit `alert:acknowledged` on a re-acknowledge (first-ack-only state-change emit).
- Do not allow Viewer or Technician to acknowledge — RBAC matrix is fixed; the negative tests pin this.
- Do not use `findOpenAlert` (the 3.4 cross-story seam at `packages/api/src/rules/findOpenAlert.ts:78`) for the `linked_alerts` lookup. The partial unique index makes a "previous OPEN alert" structurally impossible; the predecessor is always CLOSED. Use the batched `findMany({ OR: [...] })` lookup described above.
- Do not use a read-then-write (`findUnique` then `update`) for the acknowledge race — use `updateMany({ where: { id, acknowledgedAt: null } })` (compare-and-set). The read-then-write window is the exact race the partial unique index is designed to eliminate.
- Do not use `z.coerce.boolean()` for `?acknowledged` or `?cleared` — it silently coerces `"banana"` to `true`. Use `z.enum(["true", "false"]).transform(v => v === "true")` (explicit string match + typed boolean).
- Do not use `z.coerce.number()` for `?limit` without `.int()` — non-integers (`51.5`) would silently coerce to `51.5` and bypass the `.max(50)` check. The current `z.coerce.number().int().min(1).max(50).default(10)` is correct.

## Design Notes

**Why idempotent acknowledge.** A dashboard "Acknowledge" button can fire from a stale state (an alert that was ack'd in another tab, then re-rendered) or from a retry queue (network blip after the first ack committed). Returning 409 on a re-ack forces the dashboard to handle a duplicate-ack race that has no semantic value. Returning 200 with the original timestamp + original actor is the right shape — the row's state is what matters, not the request.

**Why first-ack-only emit.** The `alert:acknowledged` event semantically announces a TRANSITION (unack'd → ack'd), not a request. If the dashboard re-renders on every emit, a misbehaving client that retries would flood the channel with stale re-emits. The event carries `alert_id, acknowledged_at, actor_user_id` — the dashboard joins against its store and updates the row's `acknowledgedAt`; the idempotency check happens on the client side too.

**Why `acknowledgedByUserId` is plain `String?` and not a deferred FK.** Epic 5 owns the `User` table. Adding the FK constraint in 3.5 would block the migration on Epic 5's User landing. The plain column is forward-compatible: when Epic 5 ships, the FK constraint is added in that migration (a single `ALTER TABLE ADD CONSTRAINT`). Existing 3.4-shipped rows are valid (the column is nullable).

**Why default to OPEN-only on `GET /api/alerts`.** The dashboard's primary view shows active issues. The closed-archive view (the lifecycle audit trail) is a separate surface that requires an explicit `?cleared=true` flag. The `Alert` table grows monotonically over time; surfacing closed rows in the default view would push the OPEN alerts down the page and bury the operators' primary signal. The `?cleared=true` flag is the explicit opt-in.

**Why `linked_alerts` is predecessor history (CLOSED, not OPEN).** The partial unique index `Alert_open_unique_idx WHERE clearedAt IS NULL` (3.4's contract, `packages/db/prisma/schema.prisma:81`) enforces "at most one OPEN alert per `(device, metric, severity)`". A "previous OPEN alert" for the same key is structurally impossible — there is at most one OPEN row, full stop. The dashboard's "this alert is part of an ongoing chain" semantic therefore needs the previous CLOSED rows for the same key: the predecessor history. The single batched `findMany({ OR: [...] })` lookup (NOT one-per-row `findOpenAlert`) keeps the page query at exactly 2 round-trips regardless of page size; the `take: pageRows.length * 5` cap bounds the join. The `findOpenAlert` seam from 3.4 is reserved for the 3.4 hook path (idempotency fast-path inside the open `$transaction`); 3.5's cross-story reuse would have inverted the partial-index contract.

**Why `linked_alerts` lives on the wire (not just the server).** The dashboard renders "this alert is part of an ongoing chain" — without `linked_alerts`, the client must issue a follow-up query per row to discover the chain. Putting the predecessor history on the wire shape eliminates the N+1 on the dashboard side. The server-side cost is bounded at `limit * 5` rows (max `50 * 5 = 250` linked entries per page) so the batched lookup is not a runaway.

**Why the compare-and-set (`updateMany({ where: { id, acknowledgedAt: null }, ... })`).** Two simultaneous Operator acks on the same alert could both read `acknowledgedAt: null` and both attempt the update; the second one overwrites the first's `actor_user_id` and `acknowledgedAt`. The `updateMany` with `acknowledgedAt: null` in the WHERE is atomic at the row level — Postgres evaluates the predicate under the row's tuple lock. The first writer commits with `count === 1`; the second sees `count === 0` and follows up with `findUnique` to return the existing row. This is the same primitive pattern 3.4 used for the partial-index duplicate-open race (see `applyTransition.ts:101-141`), generalized to a column predicate instead of an index predicate.

**Why `actorUserId` is the JWT-claim `userId` (not a request header).** Headers are spoofable; JWT claims are not. The `authorize` middleware has already validated the token signature by the time the handler runs (`packages/api/src/middleware/authorize.ts:194-199`); `req.user.id` is the canonical, audit-traceable identity (the JWT `userId` claim attaches as the `.id` property in `req.user` per `AuthorizedRequest.user.id` at `packages/api/src/middleware/authorize.ts:71-86`). Sourcing the actor from a header would re-introduce the spoofing risk that the JWT layer is designed to eliminate.

**Why `now()` is injectable.** Tests assert exact wire timestamps without time-mocking libraries. The default `() => new Date()` in `packages/api/src/index.ts` keeps production code free of clock plumbing; the `now` dep is injected in the test rig as a deterministic clock. The handler uses the SAME `now()` for the DB write and the response body — no double-read drift between row and wire.

**Why post-commit emit failure is logged, not thrown.** The row is committed before the emit fires; if the emit throws (network partition, Redis-pub/sub miss), the client retry would re-fire `updateMany`, return `count === 0`, and re-return 200 — semantically a no-op. Throwing on emit failure would force the client to interpret a 500 as a write failure and retry, triggering an extra round-trip that we know will return 200. Better to log and return 200; the next eval pass / explicit refresh surfaces the ack via the REST read.

**Why no `state` field on Alert.** Alert lifecycle is `{ openedAt, acknowledgedAt?, clearedAt? }` — three timestamps, no state machine. The combination of `acknowledgedAt` (set / unset) × `clearedAt` (set / unset) gives four cells (`unack'd open`, `ack'd open`, `unack'd closed`, `ack'd closed`); the dashboard renders all four without a state field. The Incident resource has a 7-state machine (Story 4.2) because incidents flow through operator/technician transitions; alerts do not. Adding a state field would be a v2 contract bump with no v1 benefit.

**Why no `alert:cleared` emit.** Story 3.4's spec explicitly says "no socket event for clear" — the UI derives clear from a fresh reading (the de-bounce timer's falling edge). 3.5 does not introduce one either; the dashboard's alerts log re-renders when a fresh reading arrives and re-derives the row's state.

**Why no audit-log writes in 3.5.** Epic 5 owns the `AuditLog` table. Writing to a non-existent table would crash the handler. Lifecycle events use `console.warn` (mirror 3.4's pattern) so operators see `alertId, actor, acknowledgedAt` in the boot log pipeline. Epic 5 retro-fits the writes from the `console.warn` lines.
