## Why this story existed

The 2026-08-31 `/impeccable` critique flagged two structural AI-slop signatures the prior ESLint config didn't catch mechanically:

1. **Tailwind JIT scanner misses** — template-literal class interpolation (`h-[${PIN_SIZE_PX}px]`) defeats the JIT content scanner. MapView and Sidebar both shipped this pattern in v1; the Round 1 sweep migrated them to literal classes, but the rule that _would have caught them automatically_ didn't exist.

2. **Hex literals in `className` strings** — `bg-[#1E5BB8]` arbitrary-value hex classes bypass the design-token system the same way `style={{ backgroundColor: "#1E5BB8" }}` does. The new hex-literal-in-style ESLint rule (Option C) covers the inline-style case but not the arbitrary-class case.

3. **Duplicate / conflicting Tailwind classes** — `className="p-2 px-3"` (two padding utilities where one overrides) is the classic "blind copy-paste from shadcn docs" tell. No rule caught it.

`eslint-plugin-tailwindcss` addresses these via AST-level selectors. It's well-maintained (v3.18.3 ships 2024), runs in ~500ms on the Surakkha codebase, and integrates cleanly into `eslint.config.js`.

## Decisions

### Why three rules instead of seven

The original plan enabled seven rules. After install, two of them produced 31 + 24 = 55 false positives on the current codebase — well over the "zero or low single-digit false positives" target. The structural rules (`enforces-shorthand`, `enforces-negative-arbitrary-values`, `no-unnecessary-arbitrary-value`) caught 7 real instances, all canonical-form drift that's a legitimate AI-tell.

The trade-off:

- **What we lose:** mechanical catching of template-literal interpolation and class-order drift. The Round 1-3 sweeps already migrated the historical debt manually.
- **What we keep:** real canonical-form enforcement that no human reviewer catches reliably.

If we adopt Tailwind v4 (and the plugin v4 line), the static analyzer's understanding of namespaced theme tokens improves. Revisit `no-custom-classname` then.

### Absolute config path workaround

The plugin's internal `mlly.resolvePathSync` fails on relative config paths under pnpm (`url: ["."]` can't be resolved to `tailwindcss`). The workaround is to pass an absolute path via `fileURLToPath(import.meta.url)` + `dirname`:

```js
const repoRoot = dirname(fileURLToPath(import.meta.url));
// ...
config: resolvePath(repoRoot, "packages/web/tailwind.config.ts"),
```

This avoids adding a build step (no shim `tailwind.config.js` to maintain) and works from any ESLint invocation cwd.

### Whitelist (only for `no-custom-classname` if re-enabled)

If we revisit the rule later, this is the seed whitelist for design-token classes that the static analyzer can't trace:

```js
whitelist: [
  // Density tokens (theme.extend.padding.density.*)
  "p-density-card", "py-density-card", "px-density-card",
  "p-density-row", "py-density-row", "px-density-row",
  // Touch-target tokens (theme.extend.minHeight / minWidth)
  "min-h-touch", "min-w-touch",
  // Motion-duration tokens (theme.extend.transitionDuration.*)
  "duration-live-pulse", "duration-critical-pulse",
  "duration-pin-pulse", "duration-banner-fade-in",
],
```

The actual blocker is the 30+ `bg-neutral-*` / `bg-severity-*` / `bg-primary-*` classes which the analyzer flags. Each needs an entry, OR a Tailwind plugin that exposes the tokens as proper utilities.
