# Story 6.10: Tailwind-aware ESLint plugin (`eslint-plugin-tailwindcss`)

> Status: **draft** — not yet scheduled.
> Source: 2026-08-31 `/impeccable critique packages/web` follow-up; Options A+C were shipped on `ae90e3a + 8efe6e2` (prose-lint + hex-literal ESLint rule). This story covers Option B.

## Why this story exists

The 2026-08-31 `/impeccable` critique flagged two structural AI-slop signatures that the current ESLint config doesn't catch mechanically:

1. **Tailwind JIT scanner misses** — template-literal class interpolation (`h-[${PIN_SIZE_PX}px]`) defeats the JIT content scanner. MapView and Sidebar both shipped this pattern in v1; the Round 1 sweep migrated them to literal classes, but the rule that _would have caught them automatically_ doesn't exist. A future contributor can re-introduce the bug.

2. **Hex literals in `className` strings** — `bg-[#1E5BB8]` arbitrary-value hex classes bypass the design-token system the same way `style={{ backgroundColor: "#1E5BB8" }}` does. The new hex-literal-in-style ESLint rule covers the inline-style case but not the arbitrary-class case.

3. **Duplicate / conflicting Tailwind classes** — `className="p-2 px-3"` (two padding utilities where one overrides) is the classic "blind copy-paste from shadcn docs" tell. No rule catches it.

`eslint-plugin-tailwindcss` covers all three at the AST level via Tailwind-aware selectors. It's well-maintained (v3.x as of 2026), runs in <500ms on the Surakkha codebase, and integrates cleanly into the existing `eslint.config.js`.

## Acceptance Criteria

**Given** a contributor adds a Tailwind class via template-literal interpolation in a JSX attribute
**When** they run `pnpm lint`
**Then** ESLint flags the line with `tailwindcss/no-custom-classname` and an actionable message
**And** the pre-commit hook (`pnpm lint:staged`) blocks the commit

**Given** a contributor writes `className="bg-[#ABCDEF]"` (arbitrary hex class)
**When** they run `pnpm lint`
**Then** ESLint flags the line with `tailwindcss/no-arbitrary-value` (or its Tailwind-3.4 equivalent)
**And** the message references the design-token alternative

**Given** a contributor writes `className="p-2 px-3"` (duplicate padding classes)
**When** they run `pnpm lint`
**Then** ESLint flags the duplicate via `tailwindcss/no-contradicting-classname` or `tailwindcss/classnames-order`

**Given** the existing 524-test suite passes today
**When** the plugin is added
**Then** all existing tests continue to pass
**And** no class string in the current codebase trips any new rule (false-positive rate target: 0)

**Given** the plugin's class-intersection check is enabled
**When** a contributor writes `className="text-primary text-secondary"` (text two conflicting text colours)
**Then** ESLint flags the conflict

**Given** the plugin has been added and the lint is clean
**When** a contributor adds an arbitrary Tailwind class that _is_ project-permitted (e.g., a new severity colour)
**Then** they can add a single-line `// eslint-disable-next-line tailwindcss/no-custom-classname` with a comment explaining why, and the rule defers

## Scope

### Files to add

1. `eslint-plugin-tailwindcss` to `package.json` devDependencies (latest v3.x).
2. `packages/web/tailwind.config.ts` may need a `whitelist` block if the plugin flags any existing classes.

### Files to modify

1. `eslint.config.js` — add `tailwindcss` to the `plugins` object in the `packages/web/**/*.{ts,tsx}` block.
2. Enable rules:
   - `tailwindcss/no-custom-classname: error`
   - `tailwindcss/no-arbitrary-value: error` (or its 3.4 equivalent — research at install time)
   - `tailwindcss/no-contradicting-classname: error` (or its 3.4 equivalent)
   - `tailwindcss/classnames-order: warn`

### Files NOT modified

- `tailwind.config.ts` content — the existing token system stays canonical.
- `tokens.spec.ts` — class-name token coverage tests stay as they are.

## Risks

1. **False positives on existing class strings.** The codebase has ~3,500 Tailwind class usages. Even a 1% false-positive rate is 35 lint warnings. Mitigation: install the plugin on a branch, run `pnpm lint`, whitelist the legitimate cases via the plugin's config (each class can be allow-listed individually), and only then flip `warn` → `error`.

2. **Performance.** `eslint-plugin-tailwindcss` re-parses Tailwind's content paths on every lint run. The codebase has `packages/web/src/**/*.{ts,tsx}` as the content globs, which is ~85 files. Estimated lint time increase: +300-500ms. Acceptable for a pre-commit hook (which already runs ESLint on staged files only).

3. **Compatibility with the new `no-restricted-syntax` hex rule.** The two rules overlap on the `bg-[#hex]` case. The hex-literal rule (Option C) flags `style={{ backgroundColor: "#xxx" }}`; the tailwindcss rule would flag `className="bg-[#xxx]"`. Both should be `error`; a contributor who tries to bypass via either mechanism now fails both checks.

4. **Plugin maintenance velocity.** `eslint-plugin-tailwindcss` is well-maintained but tracks Tailwind versions closely. Tailwind 4.x (when adopted) will require a plugin upgrade. The version pin in `package.json` should be exact (`"3.4.x"`) rather than `^`.

5. **The pre-commit hook's `--max-warnings 0` interaction.** If `tailwindcss/classnames-order: warn` fires on a legitimate ordering preference, the commit blocks. Start with all rules at `warn` for one sprint, then promote to `error` after the false-positive rate is proven <0.1%.

## Verification

```bash
# 1. Install
pnpm add -D eslint-plugin-tailwindcss

# 2. Configure (see "Files to modify" above)

# 3. Run lint, count new violations
pnpm lint 2>&1 | grep "tailwindcss" | wc -l

# 4. Whitelist legitimate violations
# (per-file `// eslint-disable-next-line` with explanation)

# 5. Promote rules to error after one sprint of clean lint
# (i.e., on the next Story that touches a Tailwind class)
```

**Expected:** zero or low single-digit false positives on the current codebase. The Round 1-3 sweeps already migrated every known hex-literal and template-literal class to a literal token, so the historical debt is clean.

- **Test rig (if plugin recommends):** ~1 hour
- **Total:** half a day

## Open questions for the team

1. Should `tailwindcss/classnames-order` be `error` or `warn`? The codebase doesn't enforce a class-order convention today (the critique didn't flag ordering). Probably `warn` for the first sprint.
2. Should the plugin apply to `packages/web/src/**` only, or also to any future Vue/Svelte surfaces? For v1, web-only.
3. Does the existing `tailwind.config.ts` token namespace (`severity.*`, `neutral.*`, `primary.*`) interact cleanly with the plugin's class-intersection check? Probably yes (the plugin reads the config) but verify at install time.
